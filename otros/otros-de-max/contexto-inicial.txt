🏗️ Mi recomendación para la nueva estructura
1. Separar en microservicios o aplicaciones independientes
Tienes dos caminos:

Opción A (Monorepo con aplicaciones independientes): Mantener todo en un solo repositorio, pero cada "proyecto secundario" (condocdat, solutioncar, etc.) se convierte en una aplicación Django independiente que se monta dentro del proyecto principal, pero sin compartir el mismo código base. Usas un solo settings.py que carga cada aplicación como una app más, pero con sus propias rutas y vistas.

Opción B (Microservicios): Cada proyecto secundario se convierte en su propio servicio Docker con su propio código, su propia base de datos (o compartida si es necesario) y su propio dominio/subdominio. Cada uno tiene su propio Dockerfile y se despliega como un contenedor independiente, todos orquestados por Traefik.

Dado que ya usas Docker y Traefik, te recomiendo la Opción B (microservicios) porque:

Es más limpio y escalable.

Cada proyecto puede tener su propio ciclo de vida, dependencias y equipo.

Evitas conflictos de dependencias entre proyectos.

Traefik ya está configurado para enrutar por subdominios, así que es perfecto.

3. Compartir la base de datos
Si todos los proyectos necesitan compartir la misma base de datos PostgreSQL (como parece), puedes:

Opción 1: Tener un solo contenedor de PostgreSQL que sea compartido por todos los servicios. En cada docker-compose.yml de cada proyecto, en lugar de definir un servicio db, usas la red de Traefik y te conectas a un servicio db externo (que puede estar en otro compose o en la red). Esto implica que cada proyecto debe configurar sus variables de entorno apuntando al mismo host db y puerto.

Opción 2: Tener una base de datos separada para cada proyecto (recomendado para microservicios). Esto reduce el acoplamiento y permite que cada proyecto evolucione su esquema sin afectar a los demás. Si necesitas consultar datos entre proyectos, puedes hacerlo vía API.

Dado que dices que "no recuerdas si por compartir la base de datos o lo de traefik está estructurado así", mi sugerencia es separar las bases de datos a menos que haya una razón de negocio muy fuerte para compartirlas. Si las compartes, cada proyecto debería tener su propio esquema (prefijo) para evitar colisiones.

4. Traefik y la red
Actualmente tienes una red traefik_default externa que usan todos los servicios. Esto es correcto. En el nuevo esquema, cada proyecto tendrá su propio docker-compose.yml con sus servicios, y todos usarán la misma red externa traefik_default (o una red compartida). Los labels de Traefik en cada servicio definirán los subdominios.

Ejemplo para condocdat/docker-compose.yml:

yaml
services:
  app:
    image: condocdat:latest
    container_name: condocdat_app
    networks: [traefik_default]
    environment:
      - DJANGO_SETTINGS_MODULE=condocdat.settings
      - DATABASE_URL=postgres://user:pass@db_host:5432/condocdat
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.condocdat.rule=Host(`condocdat.netgogo.cl`)"
      - "traefik.http.routers.condocdat.entrypoints=websecure"
      - "traefik.http.routers.condocdat.tls.certresolver=letsencrypt"
      - "traefik.http.services.condocdat.loadbalancer.server.port=8000"
    volumes:
      - static_vol:/app/staticfiles
      - media_vol:/app/media

  # Si tiene su propia base de datos, aquí se define
  db:
    image: postgres:15
    container_name: condocdat_db
    networks: [traefik_default]
    environment:
      - POSTGRES_DB=condocdat
      - POSTGRES_USER=condocdat
      - POSTGRES_PASSWORD=...
    volumes:
      - condocdat_pg_data:/var/lib/postgresql/data

volumes:
  static_vol:
  media_vol:
  condocdat_pg_data:

networks:
  traefik_default:
    external: true
5. Reorganización del código
Elimina duplicados: Tienes muchos archivos de respaldo (models-*.py, views-*.py, settings*.py). Migra solo la versión final a un sistema de control de versiones (Git) y elimina los respaldos antiguos de la carpeta de producción.

Separa el código por proyecto: Cada proyecto debe tener su propio manage.py, settings.py, urls.py, etc. No deben estar mezclados en una sola carpeta myproject. Puedes tener un único repositorio que contenga todos los proyectos (monorepo) o repositorios separados (más recomendado).

Mantén un solo docker-compose.prod.yml por proyecto: Si cada proyecto tiene su propio compose, la gestión es más sencilla.

6. Estrategia de migración
Dado que el sistema ya está funcionando en producción, no puedes pararlo todo y rehacerlo de golpe. Te sugiero:

Crear la nueva estructura en un entorno de desarrollo (local o staging) con los nuevos directorios y compose files.

Extraer el código de cada proyecto (ej: condocdat, solutioncar) de la carpeta myproject y colocarlo en su propio directorio, ajustando sus rutas de importación y dependencias.

Crear un Dockerfile específico para cada proyecto basado en la imagen base que usas (taller_base) o en una imagen común.

Probar cada proyecto por separado con su propio compose, asegurando que arrancan y responden en sus subdominios locales (usando localhost con Traefik o directamente con ports).

Una vez probado en local, despliegas en un entorno de staging en el servidor (usando otros subdominios o puertos) para validar que todo funciona.

Finalmente, en producción, actualizas los servicios uno por uno, reemplazando los contenedores viejos por los nuevos. Puedes usar estrategias de blue-green o rolling update para minimizar el downtime.

7. Consejos adicionales
Usa un archivo .env para las variables de entorno (base de datos, secret key, etc.) y no las tengas hardcodeadas en los compose.

Considera usar un solo docker-compose.yml en la raíz que orqueste todos los servicios, pero dado que tienes muchos proyectos independientes, tener un compose por proyecto es más mantenible.

Aprovecha los volúmenes para compartir estáticos y media si es necesario. En la nueva estructura, cada proyecto tendrá sus propios volúmenes o podrás compartir un volumen común con Nginx.

Limpia tu carpeta myproject de archivos obsoletos (backups, logs, etc.) y deja solo el código fuente del proyecto principal.
